## 0. Decision summary

**Chosen architecture: Tauri 2 (Rust shell) + the existing React 19 / Vite 8 frontend, unchanged in shape.**

The webview stays the rendering engine, so the current UI, CSS Grid layout, per-panel local
edit state, debounced autosave and ~76 kB gzip bundle all carry over as-is. We only add a thin
native shell plus a small platform-abstraction layer at the few places where a browser API
does not exist in a desktop webview.

| Option | Installer size | Idle RAM | Cold start | Verdict |
| --- | --- | --- | --- | --- |
| **Tauri 2** | ~3–6 MB (NSIS) / ~4–7 MB (dmg) | lowest (system WebView, no bundled Chromium) | fastest | **Chosen** |
| Electron | 80–150 MB | 150–300 MB+ | slower | Rejected: ships a whole Chromium, contradicts "lightweight/minimal" |
| PWA only | n/a | same as web | n/a | Rejected as *the* answer: no real installer, no reliable offline window, weak file handling. Keep as-is for the web build. |
| Neutralino / Wails | ~2–5 MB | low | fast | Viable, but smaller ecosystem and worse window/webview feature parity than Tauri |

**Key trade-off accepted:** Tauri uses the *system* webview — WebView2/Chromium on Windows,
WKWebView on macOS. One codebase, two engines. Everything must be verified on both; section 5
lists the known divergences that actually affect this app.

**Same codebase stays deployable to the web** (`ggwplab.pages.dev` keeps working). The desktop
build is an additional target, not a fork. All native calls sit behind `src/platform/`, which
falls back to browser APIs when `window.__TAURI_INTERNALS__` is absent.

## 1. Non-goals (keep the plan small)

- No Electron, no bundling Chromium or Node.
- No PDF.js / pdfjs-dist unless Phase 0 proves macOS PDF viewing is unusable (see 5.1).
- No auto-updater in v1 (add later only if distribution demands it).
- No tray icon, no custom title bar, no multi-window, no native menus beyond the standard
  Edit/Window roles needed for copy-paste to work.
- No rewrite of state management, storage format, or panel components.
- No mobile targets (Tauri supports them; out of scope here).

## 2. Performance budget (verify, don't assume)

| Metric | Target | Measured (Windows, this machine) |
| --- | --- | --- |
| Windows installer (NSIS x64) | ≤ 6 MB | **1.29 MiB** (`bundle/nsis/GreatGridWorkspace_0.1.0_x64-setup.exe`) |
| macOS dmg (aarch64) | ≤ 8 MB | not built (needs a Mac) |
| JS+CSS shipped to webview | ≤ current 76 kB gzip (+ ≤ 3 kB platform layer) | **78.8 kB** JS + 2.55 kB CSS gzip; desktop-only chunk 4.94 kB, fetched lazily only in the shell |
| Cold start | < 1 s | **43 ms** warm / 231 ms cold to window handle (not first paint) |
| Idle RAM (default 2 panels) | < 120 MB | **~185 MB total**: 20 MB app + ~165 MB WebView2 process tree (shared runtime, includes GPU process). Treat < 120 MB as unreachable with a system webview; use ≤ 200 MB. |
| Panel re-render on typing | no grid re-render per keystroke | not measured (React DevTools Profiler, 10 panels) |

Guardrails for fast paint: keep `transparent: false`, no `backdrop-filter`/box-shadow animations,
no `decorations: false` custom chrome, no animated resizes. Keep the PDF iframe `loading="lazy"`.

## 5. Platform divergences this app actually hits

These are the only places where "works in the browser" ≠ "works in the shell". Fix each behind
`src/platform/`, never inline in components.

### 5.1 PDF panel (`PdfPanel.tsx` renders a remote PDF in an `<iframe>`)

- Windows (WebView2) is expected to render PDFs inline; **macOS (WKWebView) has no built-in PDF
  viewer and is the known risk** — confirm with the Phase 0 spike.
- Chosen minimal strategy, decided after the spike:
  - **If both OSes render:** keep the iframe, no dependency. Best case, zero work.
  - **If macOS fails:** keep the iframe, and on desktop show a compact "Open in default app"
    action that calls `openExternal(panel.url)` (system browser/Preview handles PDFs). Cost: ~15
    lines, 0 kB. Explicitly *not* adding PDF.js in v1.
  - **If we must render locally later:** lazy-load PDF.js only for pdf panels, bundled locally
    (not CDN) with `pdfjs-dist` worker — budget +~350 kB gzip. Treat as a Phase 8 decision.
- [ ] Remove `target="_blank"` anchors and route through `openExternal()`.

### 5.2 Drag-to-reorder panels (`PanelShell` grip) — Windows only

- Tauri intercepts OS-level drops by default, which kills HTML5 `dragover`/`drop` on Windows.
  `dragDropEnabled: false` in the window config restores it (confirmed in Tauri v2 docs).
- Consequence: OS file-drops onto the window no longer arrive as native events. The import
  dropzone must not depend on native paths — it uses `DataTransfer.files` (`File.text()`), which
  still works with HTML5 DnD enabled. Verify by dragging a `.json` onto the dropzone.
- [ ] Verify grip reorder + arrow buttons + import dropzone on Windows.
- [ ] Verify grip reorder on macOS (HTML5 DnD works there, but confirm the ghost cursor).

### 5.3 External links (`BookmarkPanel`, `PdfPanel` fallback)

- In a webview, `target="_blank"` is unreliable and usually opens nothing or an unwanted window.
- [ ] Add `openExternal(url)` in `src/platform/`: browser → `window.open(url, '_blank', 'noopener')`;
      desktop → `@tauri-apps/plugin-opener` `openUrl(url)`.
- [ ] Use it in bookmark links and the PDF "open it in a new tab" hint (keep the `<a href>` for
      accessibility/hover, but `preventDefault()` and delegate).
- [ ] Capability: allow only `opener:allow-open-url` for `http`/`https` scopes.

### 5.4 Save exported JSON (`storage.downloadWorkspace`) — macOS risk

- Blob + `link.click()` download is not guaranteed in WKWebView.
- [ ] `saveTextFile(filename, text)` in `src/platform/`:
      browser → existing blob download (unchanged); desktop → `plugin-dialog` save + `plugin-fs`
      `writeTextFile`, then a notice with the chosen path.
- [ ] Keep `serializeWorkspace()` untouched so both paths write identical bytes.

### 5.5 Import a JSON file (`ImportModal` `<input type=file>`)

- Native file input may or may not surface a picker. Prefer the native dialog on desktop.
- [ ] `openTextFile({ extensions: ['json'] })`: browser → hidden `<input type=file>` (existing
      behavior); desktop → `plugin-dialog` open + `plugin-fs` `readTextFile`.
- [ ] Keep the paste-text tab and the "Paste from clipboard" button; verify
      `navigator.clipboard.readText()` prompts/works in both webviews, otherwise fall back to
      "please press ⌘/Ctrl+V".

### 5.6 `window.confirm` in `clearAll` (`App.tsx`)

- Not implemented in WKWebView (returns falsy) → "Clear all" would silently never work on macOS.
- [ ] Replace with `plugin-dialog`'s `confirm()` on desktop and `window.confirm` on web, wrapped as
      `confirmAction(message)` in `src/platform/`. Keep the same copy, but change "from this
      browser?" to "from this device?".

### 5.7 Keyboard shortcuts (copy / paste / select-all in text panels)

- macOS WKWebView needs the standard **Edit** menu roles for ⌘C/⌘V/⌘A to reach the webview.
- [ ] In `main.rs`, set the default menu (`.menu(|h| Menu::default(h))` or
      `MenuBuilder` with App/File/Edit/Window submenus using predefined `Edit` items). Do not build
      a custom menu bar.
- [ ] Verify ⌘/Ctrl+C/V/A inside a text panel and inside the export textarea.

### 5.8 Persistence: `localStorage` in the shell

- `localStorage` works in both webviews and is stored per app data directory, so **v1 needs zero
  storage code changes.** Decide now, implement in Phase 6 only if we want it:
  - **A (default, minimal):** keep `localStorage`. No new code, no migration, no risk.
    Downside: data hides inside the webview profile, not visible/backup-able.
  - **B (recommended once the app is stable, small):** one JSON file
    `appdata/workspace.json` via two tiny Rust commands (`load_workspace`, `save_workspace`) that
    reuse the *existing* `parseWorkspace`/`serializeWorkspace` shapes. Human-readable, backup-able,
    same debounce. Cost: ~40 lines Rust + 20 lines TS; removes `localStorage` limits for long
    notes.
- [ ] Phase 0 decision recorded here; do not half-migrate.
